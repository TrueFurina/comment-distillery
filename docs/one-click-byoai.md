# 一键出报告：两条路，同一道闸门

> 决策记录 2026-10-30。本文回答三个问题：为什么改了「不内置 LLM」的落地方式、
> 一键到底怎么分叉、机验卡在哪一步。

## 一、需求

用户视角只有一件事：**给个链接，出份报告**。中间几步不该看见。

但「不内置 LLM」是既定决策（零 Key、零成本、方法论不随二进制过期）。原来的做法是
把蒸馏包交给用户，让他自己拖给 AI——**成本为零，代价是流程断在最后一步**。

## 二、解法：BYO-AI，不是内置 LLM

这两件事必须分清，否则会把铁律改掉：

| | 内置 LLM（禁用） | BYO-AI（本次采纳） |
|---|---|---|
| 模型 | 绑在二进制里 | 用户自己填 |
| Key | 工具持有/代管 | 推荐环境变量 `CD_LLM_API_KEY`（不落盘）；兜底存本机 `llm.json`（明文，已被 .gitignore 忽略），不进日志 |
| 额度 | 工具代付 | 用户自付 |
| 方法论 | 随版本固化、会过期 | 每次读磁盘上的 `SKILL.md` |

关键点：**方法论仍然每次从包里现读**。这正是不内置 LLM 的头号理由——
如果模型能力固化进二进制，`SKILL.md` 改了也不会生效。BYO-AI 没有这个问题。

## 三、一键怎么分叉

只有一个按钮，终点由「是否配了 AI」决定：

```
采集 → 预处理 → 蒸馏包 ──┬─ 未配置 ──→ 结束（mode=pack-only）
                        │             交一个能拖进任意对话框的目录
                        └─ 已配置 ──→ AI 写指南 → 机验 ──┬─ 通过 → HTML 报告（mode=full）
                                                        └─ 不通过 → 只交 md（mode=guide-unverified）
```

**没配 AI 不是失败**，是合法用法。所以不走错误分支、不弹红框。

实现上，这段语义只有一处：`core.finish_after_pack()`。GUI 与 Web 都调它——
本仓库为「两份实现各自演化」付过代价（见 `docs/engineering-pitfalls.md`）。

## 四、机验是闸门，不是附带检查

`distill()` 的循环：

1. AI 出稿 → `verify_citations` 求差集；
2. 差集非空 → 把**幻觉 ID 清单**喂回去，让它只改引用（不动观点），最多 N 轮；
3. 修不动 → `passed=False`，**不出 HTML**，只留 md 并标注"未通过"。

两个细节是踩出来的：

- **旧报告必须挪开**。重跑失败时，目录里若还躺着上一轮的 `report.html`
  （页首写着"机验通过"），用户会以为新结果成功了。`_stale_report()` 把它改名
  加 `.stale-<时间戳>`，不删。
- **prompt 里不能出现完整引用标记**。哪怕只是举例说明格式，机验也会把它当真
  引用去查，查不到就报幻觉。规则改成用文字描述（"一对英文方括号，里面依次是
  源、冒号、ID…"），并在 `smoke_distill.py` 里钉了一条断言：`"[源:" not in user_msg`。

## 五、错误处理

- AI 挂了：**不作废前三个成果**，包照常可用，`mode` 退回 `pack-only` 并带 `ai_error`。
- 未配置：`core.distill_package` 抛 `RuntimeError`，文案是"未配置 AI：缺 X，请先…"，
  不是堆栈。
- 4xx（401/403/404）：不重试，直接报"检查 base_url / model 名 / Key 是否匹配"。
  重试只会让用户多等。
- 429/5xx/网络：退避重试 2 次。

## 六、验证

| 用例 | 验什么 |
|---|---|
| `tests/smoke_distill.py` | 同进程：编排、修复循环、未过时拒绝交付、旧报告挪开 |
| `tests/e2e_web.py` | 真起 HTTP：路由注册、作业推进、结果结构、两种模式退化 |
| `tests/fake_openai_server.py` | 假网关：第一轮故意编 2 条假 ID，第二轮改好 |

端到端抓到过一个单测抓不到的 bug：`OpenerDirector.open()` 不接受 `context=`
（那是 `urlopen()` 的私有参数），传了就 `TypeError`——只在真发请求时暴露。
修法是把 `SSLContext` 绑到 `HTTPSHandler` 上，不是关掉证书校验。

## 七、明确的非目标

- 不做多轮对话式追问（那是另一个产品）。
- 不自动挑模型、不比较模型质量。
- 不把 AI 输出当定论：`report.html` 页首只承诺"引用可溯源"，不承诺"结论正确"。
- 未配 AI 时**不**偷偷降级成一个内置小模型——那会同时破坏成本承诺与方法论一致性。

## 八、补充（2026-10-30 晚）：两道闸门 + 黑话提示

实际跑起来才发现，**只查引用真实性不够**。DeepSeek 第一次写虚环那份指南时：

> 权重 ≤5 的评论共 22 条，赞合计仅 62，占全部赞的 7.5%

22 条对、62 错（实际 55）、7.5% 错（实际 6.6%）——**引用 ID 全真，数字全错**，
而 `verify_citations.py` 照样全绿。这是"看起来最可信的错误"：有引用撑着，
读者不会去复算。

### 于是加了第二道闸门：`scripts/verify_numbers.py`

它只查**能无歧义复算**的四类表述（语料条数 / 赞合计 / 最高赞 / 权重≤K 的分桶），
拿不准的一律跳过。立场是宁可漏报，不可误报——误报会让用户不再信任机验。

接进 `distill()` 后，`passed` 变成 `not bad and not numfails`。
实测构造一份"引用真、数字错"的指南，AI 死不悔改时 `passed=False`，**不出报告**。

修复轮现在会把**语料真实统计**直接喂给模型（`_corpus_stats()`），
不让它二次算错——给它"正确答案"比让它"重新算一遍"可靠。

### 第三件事：黑话提示（可选，默认关）

起因是一条评论："勒夫有节目效果跟勒夫是出有什么矛盾吗"。其中"是出"是"是畜"
的输入法漏字（V 圈把 MCN 老板称"畜"）。不懂这个梗，就会把整句读成病句。

`app/glossary.py` 做三件事，都只提示、不解释：

1. **圈内术语表**（内置约 30 个：皮套、中之人、同接、爆米、低气压……），
   只列本语料实际出现过的，频次可查；
2. **可疑写法**：同音错字（"是出"→"是畜"、"虚幻"→"虚环"）；
3. **别名组**：乐府/勒夫/府子/斧子 是同一人，**不标成错字**——
   第一版把它们当错字报出来，会让 AI 以为原文有问题。

生成的 `GLOSSARY.md` 随包走，`build_prompt` 自动带上。三条纪律写死在里面：
**宁可留空不要编释义**、明显错字注明"原文如此"、术语影响结论时说明条件分支。

最后一条最重要：**错的梗义比不懂更糟**，因为没有任何机验能发现它。
实测 DeepSeek 用了这份提示后，遇到不确定处会写"此处术语含义未完全确认"，
而不是编一个像样的解释——这正是想要的行为。

### 一个必须记住的运维坑

改完代码后，**已经在跑的服务进程不会自动加载新代码**。表现为：点"一键"后
日志一条不打、作业永远 `running`。排查了近一小时，最后发现是进程启动早于改动。
结论：改完 `app/*.py` 必须重启 Web 服务再测，否则你测的是上一版。

## 九、故障排查（2026-11-02 补）

按本节顺序排查。先分清两个命令，别混：

- `python -m app --selfcheck`：查**随包资源**是否齐全（SKILL.md、各机验脚本
  是否漏打进包），与 AI 配置**无关**。打包漏 `--add-data` 时会在这里暴露。
- `python -m app --show-config`：**查 AI 配置状态**，打印 `configured / source /
  base_url / model`（**不回显 Key**）。这是排查「能不能调模型」的总开关。

### 1. `--show-config` 显示「未配置 AI」，但本机明明有 Key
最常见，按这三步查：

- **env 没真正注入当前进程**。桥接脚本（`set-cd-env.sh` / `set-cd-env.bat`）
  必须在**同一个 shell 窗口**里先 `source` / 跑 bat，再跑 `python`。
  Git Bash 里 `source` 了、却在另一个 cmd 窗口跑 python，变量不互通。
- **Key 名不对**。工具**只认 `CD_LLM_*`**，不会自动读你系统里的
  `DEEPSEEK_API_KEY` / `OPENAI_API_KEY`（这是设计上的刻意边界，详见
  `app/llm.py` docstring——避免顺手劫持别处也在用的 Key）。桥接脚本已帮你从
  `DEEPSEEK_API_KEY` 派生 `CD_LLM_API_KEY`。
- **只给了 `CD_LLM_API_KEY` 不够**。`base_url` 和 `model` 也是必填项，
  缺一个 `configured` 仍为 `False`，`missing` 会列出具体缺哪些。
  桥接脚本默认填了 DeepSeek 的端点与模型；自定义端点时务必补齐。

### 2. 401 / 403 / 404
不重试，直接报"检查 base_url / model 名 / Key 是否匹配"。典型原因：
- Key 复制时带了首尾空格或换行；
- DeepSeek 模型名写错（常用 `deepseek-chat`，不是 `deepseek`）；
- base_url 漏了 `/v1` 后缀，或多写了斜杠。

### 3. 429 / 5xx / 超时
退避重试 2 次后仍失败，多半是网络层问题：
- 公司网络对 API 域名出口受限（本仓库开发机曾出现直连 `github.com:443`
  黑洞、但 SSH 22 通的情况，同理可能发生在 DeepSeek 端点）——换网络或代理；
- 代理下需把 `HTTP_PROXY` / `HTTPS_PROXY` 设进环境，工具走标准 `urllib`
  会自然继承。

### 4. 改完 `app/*.py` 必须重启 Web 服务
见第八节的运维坑：已在跑的进程不自动加载新代码，表现为作业永远
`running`、日志不打。重启后再测。
